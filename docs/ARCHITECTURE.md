# 架构与数据不变量

## 结构选择

`:core` 为纯 Kotlin/JVM 模块，持有数据模型、任务规则、经验算法、推荐算法和存档校验。它不依赖 Android、Room、Compose、网络或墙钟。领域函数由参数传入日期与时间，便于重复验证。

`:app` 采用单 Activity + Compose + ViewModel + StateFlow 的单向数据流。业务逻辑不放进 Composable。ViewModel 负责命令、加载与错误状态、文件选择结果和展示消息；Repository 负责事务、ID 和时间；Room 保存唯一真相源。

手动依赖注入只有 Application → Database/Repository → ViewModel/Worker，避免 1.0 引入尚未需要的 DI 框架。不是将整个系统写成一个 Activity，也不为每个类堆空接口。

## 数据表

| 表 | 关键字段 / 约束 |
| --- | --- |
| player | 固定 id=1；玩家名、服务器、存档时区、主题、提醒配置、上次提醒日 |
| goals | 主线 ID、名称、标准、归档标志 |
| quests | 任务 ID、类型、技能、强度、状态、截止/起始日、暂缓日期、关联主线 |
| completions | 完成 ID、任务 ID、发生轮次、名称/技能/类型/奖励快照、完成日期、撤销时间 |
| journal | 操作 ID、事件类型、内容、时间、可选任务 ID、展示用 XP 变动 |

唯一键是 `completions(questId, occurrence)`。一次性任务 occurrence=`once`；日常 occurrence=存档时区日期字符串。完成 ID 为 `questId:occurrence`。外键采用 RESTRICT，正常业务使用归档而不是硬删任务。

没有独立可随意修改的 XP 余额。总经验与技能经验均是 `revokedAt == null` 的 completion 快照求和。journal 是审计/展示日志，不用于余额结算，也不是一个完整的 Event Sourcing 引擎。

## 核心事务

完成任务在同一 Room transaction 中读取任务与当前轮次、判断状态、读取已有奖励记录、计算或恢复快照、写入唯一完成记录并添加日志。数据库锁和唯一键才是重复点击/并发控制的正确性边界，UI 的 busy 禁用只是体验层防抖。

撤销保存 revokedAt 并在同一事务添加负向日志。撤销后重做恢复同一条记录，不能通过改强度重复获取更大奖励。有完成历史时禁止改变任务类型，避免 once 与每日日期槽位混用。

导入必须先完成 UTF-8 解码、大小、摘要及业务校验，随后在一个事务中按外键顺序删旧/写新。事务失败应保留旧存档。删除本机存档同样是一个事务。没有 `fallbackToDestructiveMigration()`。

## 日期与等级

完成时间存 UTC epoch milliseconds；结算日期存 epoch day。日期通过玩家固定 ZoneId 算出，设备时区变化不改变当前存档规则。没有后台“每日重置数据库”的定时任务：当天槽位自然变化，不依赖应用午夜存活。

等级门槛 `50 × (level - 1) × level`，因此 Lv.1 为 0，Lv.2 为 100，Lv.3 为 300。推导函数限制有效 XP 上界，避免意外大整数导致算法溢出。等级进度每一级所需 `100 × level` XP。

本地离线产品不提供反作弊保证。修改设备时间、修改明文存档并重算摘要、创建任意任务都可能改变游戏记录；这不是支付账本或竞技排行榜。固定时区主要解决正常旅行和日期一致性，不是可信授时。

## 存档协议 v1

顶层是 JSON 对象：`format`、`version=1`、`exportedAt`、`sha256`、`payload`。`payload` 是一段 UTF-8 JSON **字符串**，摘要作用于其原始 UTF-8 字节，避免不同序列化器键顺序影响一致性。具体固定 format 值以 `BackupCodec.kt` 为准。

手写 JSONObject 编解码，无反射依赖。未来版本会被拒绝，不猜测性兼容未知 schema。非法枚举、重复 ID、断裂外键、不合法奖励、越界日期或损坏摘要均拒绝。未知的附加 JSON 字段可能被忽略，不作为往返保留协议。

SHA-256 只检测内容损坏，不是加密或防篡改签名。导出内容可被用户读取，应用明确提醒妥善保存。导入上限 8 MiB；导出超过该上限也会报错而不是输出不能恢复的备份。

**已知容量限制：** 当前 observer 每次构造一致性 World 快照，未分页。10,000 任务、50,000 完成、100,000 日志、200 主线是防御性硬上限，不是已验证性能承诺。长描述及大日志会使备份先触及 8 MiB，需在正式发布前进行真实容量压测并确定更合理的数据预算/分页或流式存档方案，不能宣传可无限存储。

## 平台副作用

每日提醒通过 WorkManager 周期轮询 + 日期/小时判断 + 数据库 claim 避免重复派发。调度并不是准点闹钟。进程死亡或权限变化可能导致当日漏发；本产品不声称 exactly-once notification delivery。通知失败会尝试释放 claim 并让系统重试。

数据库保存与 WorkManager 调度不是一个跨系统事务。保存成功但调度异常时 UI 明确提示“存档已保存，提醒调度失败”，不错误地声称数据没有改变。Application 启动时按持久化设置尝试重新配置提醒。

## 1.0 后扩展原则

引入云同步前补全冲突策略、稳定设备 ID、删除墓碑和协议版本，不直接把本地 Room 表通过任意客户端 API 暴露。引入 AI 之前明确传输授权、预算与可撤销建议；AI 不应直接授予 XP 或覆盖未确认的用户任务。

后续 Room 版本必须增加显式 Migration 和升级回归测试。首次真实 Android 构建生成的 schema 需提交；本交付没有伪造 schema。
